# WHITE Native Engine

> 原生游戏内核 — 从网页 (WebView/JS) 到真应用 (Kotlin + OpenGL ES) 的重写
> **"事同而理不同"**: 玩家看到的每个效果与原版一致, 底层实现完全是我们自己的。

## 三句宪法

1. **引擎代码 GPLv3 开源** — 谁改了并分发, 谁就开源改动
2. **Mod ABI 全开放** — 底层 Core ABI / 脚本 API / UI API 三层全部文档化, 模组许可证自由
3. **内容与代码分离** — 游戏内容 (对话/美术/音频) 版权归原作者, 以官方资源包形式分发, 不进本仓库

## 范围红线 (⚠ 最高优先级约束)

> **只动内核。资源与剧情逻辑一律不碰。**

| 不动 | 说明 |
|---|---|
| 游戏资源 | 对话文本/美术/音频/字体 — 原样读取, 不复制不改写 |
| 剧情推动逻辑 | 章节流转/分支/结局判定 — 原版代码原封不动地跑 |
| 行为表现 | 玩家看到的每个效果与原版一致 (验收标准) |

实现方式: 原版逻辑层 (JS) 经 **LogicHost 原样托管** (QuickJS/Hermes, 不修改一个字节),
原生内核只做它下面的事: 渲染/输入/音频/存储/模组宿主。
引擎对剧情层的访问是**只读观察 + 官方包装既有入口** (press/save/jump), 不重新实现。

## 渲染: 全双工双后端

```
场景指令层 (与后端无关)
    ├── GlesBackend  (OpenGL ES 2/3)  ← 默认, 全设备兼容
    └── VkBackend    (Vulkan 1.1+)   ← 高端设备, 能力检测后启用
```
启动时能力检测自动选择, 模组与逻辑层对后端**完全无感** —
同一份代码两个后端都跑, 出问题一键切回 GLES。

## 分层架构

```
┌─────────────────────────────────────────────┐
│  Mod 层 (全开放)                             │
│   · 脚本模组: JS (QuickJS 沙箱) / Lua        │
│   · 原生模组: Core ABI (C ABI via JNI)       │
├─────────────────────────────────────────────┤
│  SDK API 层 (稳定承诺, 类似 WHITE_API)        │
│   console · ui · dat · events · scene hooks │
├─────────────────────────────────────────────┤
│  引擎内核 (Kotlin)                           │
│   游戏循环 · 场景图 · 对话运行时 · 存档 · 输入  │
├─────────────────────────────────────────────┤
│  渲染层 (OpenGL ES 2/3)                      │
│   单 GLSurfaceView · 批处理 · 帧率自主控制     │
├─────────────────────────────────────────────┤
│  Android 平台层                              │
│   Activity · 前台服务保活 · 存储目录           │
└─────────────────────────────────────────────┘
```

## 为什么能赢过 WebView

| 痛点 (网页版) | 原生方案 |
|---|---|
| 30 个 canvas 分层合成, GPU 每帧全量过一遍合成器 | **1 个** GLSurfaceView, 一条渲染路径 |
| JS GC 停顿掉帧 | Kotlin 对象池 + 无 GC 热路径 (顶点缓冲复用) |
| rAF 受 Chromium 节流, 切后台被杀 | 自主渲染循环 + 前台 Service |
| 每层桥接损耗 (JS→合成器→驱动) | Kotlin → GLES 直达驱动 |
